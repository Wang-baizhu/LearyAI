更新当前运行上下文对应知识库的 canvas。

**何时使用：**

* 已经根据知识库内容整理出一版关系图，希望直接更新知识库全局视图
* 需要用当前生成的关系图结果直接替换知识库当前关系图
* 当前阶段目标是输出一张“以资源节点为主、关系清晰、节点尽量少”的关系图，而不是展开完整概念图谱
* 当前阶段优先表达“文档 - 模板 - 模板”的直接关系，尤其是同文档下的 `mindmap`、`quiz` 之间的对应、依赖、并列、前置关系

**参数：**

* `summary`（字符串，必填）—— 本次关系图更新结果的简短总结
* `canvas`（对象，必填）—— 候选 canvas 快照，必须包含：
  * `version`
  * `nodes`
  * `edges`
  * `viewport`（可选）

`canvas` 的结构约束如下：

* 顶层仅允许使用当前白板快照相关字段，至少应包含 `nodes`、`edges`
* `version` 如果传入，必须是整数
* `viewport` 如果传入，必须是对象，且 `x/y/zoom` 必须是数值
* 节点策略优先级如下：
  * 第一优先：复用当前知识库已有资源节点
  * 第二优先：通过资源节点之间的边直接表达关系
  * 第三优先：只有在无法表达时，才允许极少量新增非资源节点
* 默认把“文档节点 + 模板节点 + 模板之间的关系边”视为主体，不要把核心语义藏到 annotation 或抽象节点里
* 当前阶段应尽量只使用当前 resource 的节点，不要默认生成大量 `root:*`、`topic:*`、`skill:*`、`strategy:*`、`type:*` 这类派生节点
* 如果仅靠资源节点之间的关系已经可以表达知识结构，就不要再额外创建抽象中间节点
* 如果一个模板明显对应某个文档，就优先直接连接 `kbdoc:{docId}` 与 `template:{templateId}`
* 如果一个 `quiz` 与某个 `mindmap` 明显围绕同一知识点，就优先直接连这两个模板节点，不要只让它们都各自连到文档
* 如果两个 `quiz` 之间存在先后、递进、对照、互补关系，也直接在两个 quiz 节点之间建边
* 每个 `node` 必须包含：
  * `id`
  * `type`
  * `data`
  * `data.label`
* `node.type` 目前只允许：
  * `resizable`
  * `annotation`
* `node.position` 可以省略
* 如果传入 `node.position`，则必须满足：
  * `position.x` 是数值
  * `position.y` 是数值
* 不要把节点主标题放在顶层 `label`，应写入 `data.label`
* 文档节点 id 必须稳定，使用 `kbdoc:{docId}`
* 模板节点 id 必须稳定，使用 `template:{templateId}`
* 新增非资源节点时必须谨慎，且 id 需要稳定、语义明确；不要为了分组或美观而随意造节点
* 文档节点和模板节点应作为关系图主体，优先围绕这些节点建立连接
* 每个 `edge` 必须包含：
  * `id`
  * `source`
  * `target`
* `edge.label` 强烈建议填写，使用简短、明确的关系词，例如：
  * `前置`
  * `支撑`
  * `并列`
  * `扩展`
  * `应用于`
  * `依赖`
* `edge.sourceHandle`、`edge.targetHandle` 不是必须字段
* 如果没有明确的端口布局需要，优先不要传 `sourceHandle`、`targetHandle`
* 边应优先表达资源节点之间的直接关系，不要为了补齐概念树而制造大量“资源 -> 抽象节点 -> 抽象节点”的链路
* 优先输出如下几类边：
  * 文档 -> 模板：`来源`、`基于`、`产出`
  * mindmap -> quiz：`对应`、`支撑`、`覆盖`、`映射`
  * quiz -> quiz：`前置`、`递进`、`对照`、`互补`
  * 文档 -> 文档：`引用`、`扩展`、`补充`
* 不要生成语义重复的边；如果两条边表达的是同一种关系，只保留一条
* 不要同时生成两套仅 `id` 不同、但 `source/target/label` 实际重复的边
* `edge.source` 与 `edge.target` 必须引用 `nodes` 中已存在的节点 id
* 关系图应优先保持“少节点、强关系、可读性高”，而不是追求概念层级铺满
* 同一个文档下如果同时有 `mindmap` 与多个 `quiz`，优先形成“小型关系簇”：
  * 文档节点作为文档锚点
  * `mindmap` 作为知识主节点
  * `quiz` 作为围绕知识点展开的关系节点
* 如果跨文档存在明确关联，也可以直接保留跨文档边，但不要因此复制节点或新建过多桥接节点
* 除非确实无法表达，否则不要把“知识点名称”单独造一个抽象节点；优先把关系写在边标签上

**约束：**

* tool 会自动读取当前 runtime context 中的 `project_id`、`kb_id`、`user_id`
* tool 会直接使用你传入的 `canvas` 更新知识库当前关系图
* 若候选 canvas 不满足上述结构约束，tool 会直接报错，不会更新知识库
* 这是全量替换语义，不会自动保留旧图中的 annotation、布局、viewport 或抽象节点
* 当前阶段如果资源节点已经足够表达结构，请不要主动扩展出额外的知识图谱层
* 你的目标不是生成“概念树”，而是生成“资源关系白板”：用户应该一眼看出文档、模板以及模板间的关系

**替换行为说明：**

* 你传入的 `canvas` 会直接作为新的知识库关系图写入，不会和旧图做 merge
* 因此如果你希望保留某个节点、边、annotation 或 viewport，必须在这次提交的 `canvas` 中显式带上
* 如果你不再希望旧的抽象节点、旧边、旧标注继续存在，只要不要在本次 `canvas` 中输出它们
* 推荐理解方式：
  * 你负责产出“当前完整想要保留的关系图”
  * tool 负责校验结构并把这份结果整体写入知识库
  * 所以当前阶段最稳妥的策略是：优先复用稳定资源节点 id，减少非资源节点数量，只输出最终想展示的必要关系

**返回：**

* 更新结果摘要
* 额外返回更新后的 canvas 结果供调试使用
